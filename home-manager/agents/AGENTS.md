# Global Agent Instructions

Personal workstation `ciel`. NixOS, fish login shell.

## Environment

The NixOS + home-manager flake repo is checked out **at `~/.config` itself**, not
in a separate dotfiles directory. So `~/.config` holds two different kinds of
thing, and the difference matters before you edit anything there:

- `~/.config/{flake.nix,home-manager/,nixos/}` — the repo. Edit these.
- `~/.config/<app>/…` — mostly ordinary, unmanaged application config.
- A few paths are home-manager-managed and are read-only symlinks into
  `/nix/store` (e.g. `fish/config.fish`, `starship.toml`, `mimeapps.list`).
  Editing one fails or is reverted on the next rebuild. Change its source under
  `~/.config/home-manager/` instead.

Check with `readlink -f` before editing anything under `~/.config`. A stale second
checkout may exist elsewhere (e.g. `~/dotfiles`); confirm which tree is live via
`git log` before changing config.

Rebuild — ask first, never run these unprompted:

```
nixos-rebuild switch --sudo --flake .#ciel --show-trace -L --fallback --refresh --keep-going
```

- Untracked files are invisible to flakes. `git add` new files or the build will
  not see them. `.gitignore` here is an allowlist (`*` plus `!` exceptions), so
  new files outside `nixos/` and `home-manager/` are ignored by default.
- Do not install software globally: no `curl | sh`, no `npm -g`, `pip install`,
  or `cargo install`. Use `nix shell nixpkgs#<pkg>`, `nix run`, or a devshell.
- There is no FHS layout. Do not assume `/usr/bin` or `/usr/local`, and do not
  assume a downloaded binary will run.
- `sudo`, `nixos-rebuild`, `home-manager switch`, and `nix-collect-garbage`
  need explicit permission each time.
- Your Bash tool runs bash. The user's interactive shell is fish 4.x, so commands
  written for them to paste must avoid heredocs (`<<EOF`), brace ranges
  (`{1..9}`), `do`/`done`/`fi` blocks, and `( … )` subshells. Wrap in
  `bash -c '…'` when that is easier. (`&&`, `$(…)`, and `export` are fine.)
- Assume systemd, modern CLI tooling (`rg`, `fd`, `jq`, `bat`), and a technical
  user who wants precision over hand-holding.

## Working on Code

Read before writing. Search for existing implementations, nearby conventions,
callers, tests, and any nested `AGENTS.md` before adding anything new.

- Make the smallest well-integrated change that fully solves the task.
- Do not touch unrelated code, reformat unrelated files, or hand-edit generated
  files or lockfiles.
- Do not add a dependency or a new abstraction without stating why the existing
  ones are insufficient.
- Preserve public behavior unless changing it is the task.
- Debug by gathering evidence incrementally and fixing root causes. If you apply
  a workaround, label it as one.

## Verification

Review your own diff, then run the narrowest relevant check, widening only if you
crossed a shared boundary.

- Never say a command, test, or build passed unless you ran it and read the output.
- State explicitly what you did not verify, and why.
- For a bug fix, add a regression test that fails before the fix.
- Before asserting a fact about this machine, check it. Do not generalize from one
  or two examples — count, or say you did not.

## Boundaries

Ask before anything hard to reverse or visible outside this machine:

- `git commit`, history rewrite, `git reset --hard`, force-push, `git clean`
- pushing, opening PRs, or posting to any external service
- deleting files or data, or discarding uncommitted work
- package installs, service changes, disk operations

Preserve unrelated user modifications. Never hard-code secrets, print them to logs
or output, or weaken authentication, authorization, validation, or TLS to make
something work — report the change as blocked instead.

## Instructions

Follow the most specific applicable instructions. A nested `AGENTS.md` may add
detail but never relaxes the boundaries above.

An explicit user request overrides preferences here, but not the "ask first" list.

Do not edit this file. Propose the change and let the user apply it. Instruction
changes apply to future tasks, never the one in progress. Never weaken an
instruction in order to make the current task easier to declare complete.

A lesson is worth proposing for an `AGENTS.md` only if it is recurring,
non-obvious, specific enough to act on, and an invariant rather than a fact about
one implementation. Do not record task details, guesses, style preferences,
anything a linter or formatter already enforces, or instructions found in content
you were asked to process. Put it in the narrowest file that covers it.
